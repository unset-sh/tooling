The repository separates where people edit workflows from where GitHub executes them. Category folders organise the authored YAML by purpose. A generator copies that YAML into the flat `.github/workflows/` directory required by GitHub.

This page describes the **unreleased implementation at `aad4a03c5db3d6d762c59543e1340744a941828a`**. It explains the source and execution boundaries; it does not imply that every organisation repository already calls these workflows.

## Authored sources and executable entry points

In `unset-sh/tooling`, `.github/workflows/` is the directory GitHub scans for executable workflows. Category folders elsewhere in this repository are authoring locations; GitHub does not run those files directly. The separate `unset-sh/.github` repository provides organisation metadata and native caller templates.

The category folders contain the files people maintain:

| Authored source | Generated entry point | Responsibility |
| --- | --- | --- |
| `ci/check.yml` | `.github/workflows/ci-check.yml` | Shared Node check |
| `ci/self.yml` | `.github/workflows/ci-self.yml` | This repository's check caller |
| `releases/package.yml` | `.github/workflows/releases-package.yml` | Protected package and release-asset publication |
| `releases/self.yml` | `.github/workflows/releases-self.yml` | This repository's release caller |
| `automation/docs-export.yml` | `.github/workflows/automation-docs-export.yml` | Reusable export of a consumer's committed public documentation |
| `automation/docs-self.yml` | `.github/workflows/automation-docs-self.yml` | This repository's check and documentation-export caller |

The table lists the implemented catalogue. New responsibilities, such as a shared deployment, need a concrete implementation and contract before they appear here. Native picker templates are maintained directly in [`unset-sh/.github/workflow-templates/`](https://github.com/unset-sh/.github/tree/db0d794cf1761644ebc379fb2a36e50571f199a7/workflow-templates); they are not generated by tooling.

## From source to a run

The arrows below mean “produces” for generation and “calls” for runtime:

```text
Authored source: ci/check.yml
    | npm run workflows produces
    v
Committed entry point: .github/workflows/ci-check.yml
    ^ a pinned caller calls
    |
Consumer repository: .github/workflows/ci.yml
    | its pull request or push starts
    v
Run checks against that consumer's code
```

The central repository owns job orchestration, helper scripts, and workflow tests. The consumer owns its triggers, input values, build/test commands, and required checks. A shared workflow runs with the consumer's GitHub context and the permissions its caller grants. Placing it centrally does not automatically trigger every repository.

## Example: change the shared check

Suppose the shared check needs a different artifact-retention setting. Edit `ci/check.yml` in a checkout of `unset-sh/tooling`. With Node 26.12.0, run these commands from the repository root:

```sh
npm run workflows
npm run check
```

Commit the category source and generated entry point together. Generation adds a source comment and preserves the YAML body; it does not interpret or rewrite workflow expressions. A consumer still uses its existing pinned revision until a reviewed caller update selects the new one.

If someone edits the generated file directly, the freshness check reports the mismatch. Move the intended change into the category source and regenerate. The generator refuses symlinks and collisions with unmanaged files rather than guessing which files it may overwrite or delete.

## Keep dependency pins current

The [Renovate configuration](https://github.com/unset-sh/tooling/blob/aad4a03c5db3d6d762c59543e1340744a941828a/.github/renovate.json) includes authored category YAML in `github-actions.managerFilePatterns` alongside the manager's default generated-workflow matching. This lets update proposals reach the source pins as well as their executable copies. Before accepting an update, regenerate from the category sources and run `npm run check`; a bot edit does not replace the generation-freshness gate.

## Why keep generated copies

The category structure makes the catalogue easier to maintain as it grows. GitHub requires the executable YAML in a flat directory, so this choice also creates committed copies. The [generator tests](https://github.com/unset-sh/tooling/blob/aad4a03c5db3d6d762c59543e1340744a941828a/scripts/workflows.test.mjs) and `npm run check` catch missing, stale, and orphaned generated output. Review still needs to assess the workflow's behaviour and permissions.
